# 筋骨智策 OsteoSarc-Agent

**基于可计算循证指南与多智能体协同的骨质疏松肌少症全周期智能决策平台**

一个主智能体 + 六个子智能体，跑在一份**可计算**的指南语料上：每条推荐都带着一段
机器可判定的适用条件，所以系统回答的不是"哪几段文字提到了这个病"，而是
**"哪几条推荐对这位患者成立、哪几条被排除、为什么"**。

```bash
python -m osteosarc_agent assess --case demo     # 完整评估报告
python -m osteosarc_agent conflicts --case demo  # 只看指南分歧
python -m osteosarc_agent ui --port 8000         # 可视化控制台
python -m unittest discover -s tests -v          # 测试
```

零依赖，Python 3.10+，标准库即可运行（含 HTTP 服务与控制台页面）。

---

## 这个平台想解决的问题

骨质疏松门诊最常见的失败模式，不是"没诊断出来"，而是几件具体的事：

* 病人因脆性骨折来看病，**处理了骨折，没处理骨质疏松**；
* 肌少症用哪套标准判，**不同标准对同一个病人给出不同结论**，而报告里只写一个；
* 指南之间**真的有分歧**（极高风险者先用促骨形成药还是双膦酸盐？CKD 合并肌少症的
  蛋白目标是 1.2–1.5 还是 0.6–0.8？），而系统把五段文字拼在一起交给医师；
* **缺的数据被当成正常值**：没测肌量的病人被判成"肌少症风险低"；
* 用药安全检查**漏跑一项**，报告看上去却是完整的。

这七件事分别对应下面六个 Agent 的设计取舍。

## 语料：把指南变成可计算的对象

内置语料覆盖近十年中西医、国内外的相关指南与共识——骨质疏松、肌少症、骨肌共病、
老年运动康复、老年营养、跌倒、用药安全——共 **30 部指南 / 86 条推荐 / 58 个临床问题**，
跨 **5 个地区**（中国、美国、欧洲、亚太、国际）与 **7 个证据体系**
（现代医学、中医、老年医学、肌少症专业、营养、康复、临床药学）。

每条推荐长这样（`osteosarc_agent/guidelines/library/*.json`）：

```json
{
  "rec_id": "CN.OP.2022.DENOSUMAB_CKD",
  "question": "q.pharm.ckd_agent_choice",
  "action": "start_denosumab",
  "direction": "consider", "strength": "conditional",
  "statement_zh": "地舒单抗不经肾脏清除，肾功能不全者可考虑使用，但低钙血症风险……",
  "applies_when": {"all": [{"fact": "dx_osteoporosis", "op": "is_true"},
                           {"fact": "egfr", "op": "<", "value": 35}]},
  "excluded_when": {"fact": "hypocalcemia", "op": "is_true"}
}
```

三条设计决定：

**三值逻辑。** 判定结果是 `true / false / unknown`。临床记录不完整远比记错常见，
所以缺一个事实不会塌缩成"不适用"——它会传播成 `unknown`，在界面上显示为
"需补充数据"，而不是悄悄丢掉一条可能最重要的推荐。

**排除优先。** `excluded_when` 命中就是不适用，哪怕 `applies_when` 也命中。
这条不对称是有意的：语料里的排除条件是禁忌证，一条会输掉平局的禁忌证不叫禁忌证。

**装载即校验，失败关闭。** 谓词引用的每个 `fact` 必须在事实词表里声明过、
每条推荐的 `question` 必须在问题目录里登记过——否则**拒绝装载**。
一个拼错的事实名会让条件永远无法判定，一个未登记的问题会让推荐永远单独成组、
永远读作"一致推荐"，这是最安静的失效方式。

> ⚠️ **语料声明**：仓库内置的全部条目都是公开指南要点的**编辑性转述**，
> 不是授权原文（`provenance: editorial_paraphrase`）。控制台每一屏都会显示这一点。
> 落地时用 `--corpus` 指向本机构获授权的语料目录替换即可，格式见
> [docs/GUIDELINES.md](docs/GUIDELINES.md)。

## 一个主智能体 + 六个子智能体

```
病例结构化 → 骨肌诊断 → 风险预测 → 循证决策 → 指南冲突消解 → 安全审查与随访
```

顺序不是排版，是数据依赖：诊断要等结构化推导出 `asmi`、`tscore_min`、钙与维 D 标志；
指南谓词要等诊断和风险把 `dx_*`、`*_risk_tier`、`very_high_fracture_risk` **回写**
到共享事实空间——正是这个回写，让语料里可以直接写"适用于极高骨折风险者"，
而不必在每条推荐里重新推导一遍。

### 1. 病例结构化 Agent
读入年龄、性别、绝经史、脆性骨折、DXA 与腰椎/髋部 BMD、握力、步速、5 次起坐、肌肉量、
实验室、用药史、跌倒史、营养与中医四诊，归一到 122 个已声明的事实，并推导 BMI、ASMI、
控制性 T 值、CKD 分期、校正血钙、维 D 分级、用药类别、跌倒风险药物计数、多重用药。

有价值的输出不是它找到的字段，而是它**没找到**的：`missing_critical` 列出每一项缺失
**会挡住哪个下游决策**（"缺 eGFR —— 未查肾功能不得启动抗骨吸收治疗"）。

### 2. 骨肌诊断 Agent
**一次调用同时判骨与肌**，不是两次会诊。理由有二：同一项测量服务两个诊断
（5 次起坐 16 s 既是肌少症功能判据、又是跌倒标志、还通过跌倒抬高骨折风险），
分开跑会问两遍、只用一遍；而共病本身是独立诊断，有一套两病共享的干预内核。

肌少症侧**三套标准全跑**并列出结论与各自依据——AWGS 2019 / EWGSOP2 / GLIS 2024。
参考病例（78 岁女性，握力 17 kg，5 次起坐 16 s，未测肌量）得到三个不同答案：

| 标准 | 结论 | 为什么 |
| --- | --- | --- |
| AWGS 2019 | 可能肌少症（可先行干预） | 握力 17 < 18；5 次起坐 16 ≥ 12；肌量未测 |
| EWGSOP2 | 可能肌少症（probable，待确诊） | 握力 17 **不低于** 16，但 5 次起坐 16 > 15 触发肌力下降 |
| GLIS 2024 | 无法判定 | 肌量为必备核心要素，未测即不能确诊 |

系统还会说明**分歧从哪来**："握力 17 kg 落在切点之间"、"5 次起坐在两套标准里归属不同的轴"、
"补测 ASMI 可让三套标准收敛"。把三个结论并排给出，比替医师选一套更有用。

### 3. 风险预测 Agent
输出五轴而不是一个标签：**骨折 / 跌倒 / 肌少症 / 营养 / 功能衰退**。
一个因为骨脆而极高风险的病人，和一个因为总摔跤而极高风险的病人，方案完全不同。

三条诚实性约束：

* 它**不是 FRAX**，也不是经验证的预测模型。FRAX 系数不公开、无法复现；这里是指南
  自己点名的危险因素的透明加权合成，每一轴都列出驱动因素与权重，可以被反驳。
* **缺数据降低置信度，不降低分数**。某一轴关键输入缺一半以上且分数落在"低"档时，
  分层显示为**未评估**而不是"低"——把没做的检查渲染成一块令人安心的绿色，
  是这张雷达图能犯的最危险的错误。
* 骨折**分层**以指南分层规则为准（近期骨折、T ≤ -3.0、治疗中骨折……），
  合成分数只用于比较各轴权重；两者不一致时以规则为准，并写明覆盖原因。

### 4. 循证决策 Agent
把整份语料对着这位患者跑一遍，分成四桶：**适用 / 已排除 / 不适用 / 数据不足**。

"已排除"这一桶在临床上比"适用"更响：`eGFR 32 < 35` 把双膦酸盐条目整体拿下桌面，
这是一个发现，不是一个缺席，所以它被保留、被引用、被显示。

"数据不足"这一桶被转成**带优先级的补测清单**："补测「四肢骨骼肌质量指数」可解锁 4 条
推荐的适用性判定"——比一句"建议完善检查"有用得多。

### 5. 指南冲突消解 Agent
按**临床问题**分组，每个问题给一个判读：

| 判读 | 含义 |
| --- | --- |
| **一致推荐** | 适用条目方向一致 |
| **条件推荐** | 方向一致但强度为有条件，或仅有单一来源 |
| **存在争议** | 真分歧：同一措施上方向相反，或互斥问题上给出不同答案 |
| **不适用于本患者** | 该问题下条目全部被排除或适用条件不成立 |

数据还逼出了两个额外状态，把它们塞进上面四类都是撒谎：

* **争议已被本例事实消解** —— 指南之间确实有分歧，但这位患者自己的事实拿掉了一方。
  `eGFR 32` 去掉双膦酸盐一线的立场，于是"极高风险者先用哪类药"这个国际分歧
  **在本例中有确定答案**。报成"一致推荐"会掩盖答案依赖于一个化验值；
  报成"存在争议"则把病历已经做出的决定又推回给医师。
* **数据不足，无法判定** —— 关键事实缺失导致适用性无法判定。

**互斥 vs 互补**是这里的关键区分，由问题目录里的 `exclusive` 标注决定：
"增加跌倒风险的药物如何处理"下三部指南给出三个不同动作，那是三条互补的指令；
"极高骨折风险者的初始药物选择"下两个不同动作，那是真分歧。没有这个区分，
冲突检测要么对每个多来源话题狼来了，要么漏掉真正要紧的分歧。
另外支持 `subsumes`：「每日至少 1.0 g/kg」被「1.2～1.5 g/kg」蕴含，两者不算分歧。

**争议存活时，平台不选边**。它给出双方立场、各自的适用条件、本例可用于权衡的患者特异性
因素，以及在有明确处理方式时的**平台策略**（例如蛋白目标：不输出单一数字，
转为要求肾脏科与营养科共同设定并动态监测）。

### 6. 安全审查与随访 Agent
最后跑，顺序固定：**禁忌证 → 药物相互作用 → 肾功能 → 低钙风险 → 跌倒风险 → 依从性 → 随访节点**。

顺序即设计：在不知道肾功能之前查相互作用，产出的是一份关于本来就不该给的药的漂亮报告；
钙的门必须在任何抗骨吸收药下达**之前**关上，而不是之后。

两条平台自律：

* **漏跑的检查必须被报成漏跑。** schema 要求 `checks_run` 含全部七项，缺项的输出被**拒收**——
  一份有静默缺口的安全报告，比没有报告更危险，因为它看起来是完整的。
* **阻断即阻断。** `blocking` 非空时整次运行标记为 `needs_action`，方案里的药物卡片被打上
  ⛔ 并写明是哪几条挡住了它。

随访按这位患者**将要接受什么**生成：CKD 背景下的地舒单抗路径会拿到用药后 1～2 周与 1 个月
的加查血钙（说明书警示），双膦酸盐路径不会。最终落到**即刻 / 3 个月 / 6 个月 / 12 个月**四档。

## 个体化治疗路径

三栏：**骨保护 / 运动与训练 / 营养**。一条不变式贯穿这一层：

> **没有在本例中成立的证据，就不生成这条方案。**

方案规则只有在临床触发条件成立**且**它指名的支持性推荐至少有一条判定为"适用"时才出现。
支持性证据被排除的规则不出现，并且带着原因进入 `suppressed` 列表——那份列表往往更有教益
（"分级冲击性负荷 ← EU.ROS.2018.IMPACT_GRADED：高跌倒风险"）。

于是控制台上每张卡片的「查看循证依据」**按构造**都有东西，而不是靠祈祷；
换一份授权语料，方案随之改变，这正是把指南做成可计算的意义。

**平台不产生任何剂量。** 给药方法（空腹、直立 30 分钟、与钙剂间隔）与监测间隔是安全信息，
会写；"这位患者给多少毫克"是医师的决定。

## 控制台

```bash
python -m osteosarc_agent ui --port 8000
```

单页、无 CDN、无构建步骤，默认只绑定 `127.0.0.1`。布局对应产品设想：
左侧**患者数字画像**、中间**骨肌风险雷达 + 三标准诊断**、右侧 **AI 判断**，
下方**指南冲突消解**与**个体化治疗路径**（每条右侧一个「查看循证依据」），
最下方**安全审查与随访计划**。

点开证据抽屉看到的不只是指南原句，还有**适用性推演树**——哪几条事实让这条推荐在
这位患者身上成立，逐个节点标注 ✓/✗/?。详见 [docs/CONSOLE.md](docs/CONSOLE.md)。

## 可选的表述层

平台在**没有配置任何模型时完整运行**。配置模型后，它只是叙述器：把已经确定的结论改写成
两段可读的文字，然后接受校验——

* **剂量扫描**：出现确定性结论里没有的"数字 + 剂量单位"，整段丢弃（不是修补，是丢弃）；
* **药名白名单**：肯定语境中提到流程没有提过的药，或提到本例已排除的药物类别，丢弃
  （"不宜使用阿仑膦酸钠"可以写，"可以考虑阿仑膦酸钠"不行）；
* **放行式表述**：存在阻断性或高风险发现时出现"未见明显异常"，丢弃。

被拒的叙述回退到确定性摘要并写明原因。结构化决策始终是产品，叙述只是它上面的便利层。

```bash
export OSTEOSARC_LLM_PROVIDER=anthropic OSTEOSARC_LLM_API_KEY=... OSTEOSARC_LLM_MODEL=...
python -m osteosarc_agent assess --case demo --llm anthropic
```

## 命令

| 命令 | 用途 |
| --- | --- |
| `assess --case demo [--json]` | 跑完整评估并输出报告 |
| `assess --file ./case.json` | 跑自己的病例（JSON，字段名见事实词表，支持别名与一层嵌套） |
| `conflicts --case demo [--all]` | 只看冲突消解 |
| `guidelines [--stats\|--list\|--questions\|--show REC_ID]` | 查看与校验语料 |
| `agents` | 列出主智能体与六个子智能体 |
| `demo` | 三个示例病例并排对比 |
| `ui --port 8000` | 启动控制台 |

`assess` 的退出码带状态：`0` 完成、`2` 存在阻断性问题、`3` 有环节失败——
脚本可以据此 gate。

## 三个示例病例

它们各自触发平台不同的行为，不是同一件事的三个例子：

| 病例 | 触发的行为 |
| --- | --- |
| `demo` 78 岁女性 · 椎体骨折 · eGFR 32 | 三标准分歧；一线药物之争**被 eGFR 消解**；蛋白目标之争**存活** |
| `sparse` 82 岁男性 · 髋部骨折术后 · 资料极少 | 三项阻断性安全门；四轴**未评估**；补测优先级清单 |
| `gc_male` 72 岁男性 · 长期激素 · 肾功能正常 | 握力落在切点另一侧（AWGS/GLIS 判肌少症，EWGSOP2 不判）；蛋白之争**因 eGFR 78 消解** |

## 边界

本平台是**临床决策支持**，不是诊疗行为，不替代医师判断。所有结论须由医师核对指南原文后使用。
内置语料为编辑性转述而非授权原文；风险评分为透明合成而非经验证的预测模型；
平台不生成任何药物剂量。请在使用前阅读 [docs/LIMITATIONS.md](docs/LIMITATIONS.md)。
